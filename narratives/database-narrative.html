Artifact Description

The artifact I selected for the database category is my AnimalShelter Python class, which I originally created during CS 340 Client/Server Development; the original file header is dated October 8, 2025. The class connects to the AAC MongoDB database and provides create, read, update, and delete operations for animal records in the animals collection. I selected the same core artifact for this milestone because the database layer is central to how the application works. The original project already demonstrated basic MongoDB connectivity and CRUD operations, but it gave me room to improve how the application handles credentials, validates database requests, manages indexes, performs queries, and uses MongoDB for server-side analysis.

For Milestone Four, I created Enhanced_AnimalShelter_Database.py as a database-focused version of the artifact. I kept the software-design improvements from my earlier enhancement, including the MongoConfig configuration object, custom exceptions, structured logging, dependency injection, connection verification, and clean resource management. I then added features that are specific to database design and administration. These include environment-based configuration, safer MongoDB query handling, server-side sorting and pagination, document counting, reusable single-field and compound indexes, aggregation pipelines, index inspection, and query-plan explanation. The result is still recognizable as the AnimalShelter class from CS 340, but the database interface is much closer to the way I would want to structure a maintainable application.

Why I Selected the Artifact and How It Was Improved

I selected this artifact because it lets me demonstrate database skills in a working application instead of showing isolated MongoDB commands. The class is responsible for the boundary between the Python application and the database, so changes at this layer affect reliability, performance, security, and the amount of data that has to move between MongoDB and the application. That made it a viable choice for showing that database work involves more than storing records. It also involves deciding how queries are constructed, where processing should occur, how access is protected, and how the database can be tuned for common operations.

One important improvement is credential handling. The original artifact accepted a username and password directly, which is convenient for a classroom exercise but can encourage credentials to be placed in source code. The enhanced MongoConfig class adds a from_environment() method so connection information can be loaded from environment variables. The connection URI also escapes credential values before they are inserted into the URI, and the logger records only the host, database, and collection instead of the complete URI. These changes do not replace MongoDB authentication or operating-system security, but they reduce the chance that a password is exposed through source control or application logs.

I also strengthened query and update handling. MongoDB queries are flexible because operators can be nested inside dictionaries and lists, but that flexibility means the application should not accept every possible operator without review. I added recursive query validation that blocks server-side JavaScript-related operators such as $where, $function, and $accumulator. For updates, the class supports a defined set of common operators and rejects unsupported operators or a mixture of operator and non-operator fields. Update and delete methods also require a nonempty filter. This is especially important when the many option is used because an empty filter could unintentionally modify or delete a considerable portion of the collection.

The performance portion of the enhancement moves more work to MongoDB when that is the better choice. The read method now supports server-side sorting, skipping, and limiting, which makes it possible to page through results without retrieving the full result set and sorting it in Python. The count method uses count_documents(), and aggregate_by() builds a MongoDB aggregation pipeline that can filter, group, count, sort, and limit results on the server. This is different from my Milestone Three algorithms enhancement, where I intentionally used in-memory algorithms to demonstrate merge sort, binary search, and dictionary indexing. In this database milestone, the goal is to let the database engine perform the work it is designed to handle efficiently.

I added ensure_indexes() to create indexes on breed, animal_type, outcome_type, and a compound animal_type/breed key. The breed index also connects back to the indexing work I completed in CS 340. The compound index demonstrates that index design should reflect real query patterns rather than adding unrelated indexes. Because indexes improve many reads but also require storage and maintenance during inserts and updates, I also added get_index_information() explain_query(). These methods make it possible to inspect the indexes that exist and review MongoDB query plans when deciding whether an index is being used. The accompanying unit-test file contains eleven tests covering configuration, query validation, CRUD compatibility, sorting and pagination, counting, index creation, aggregation, and query-plan handling.

Course Outcome Coverage

This enhancement meets the main course outcome I planned for the database category: demonstrating the use of well-founded techniques, skills, and tools in computing practices to implement solutions that deliver value. MongoDB is no longer used only as a storage location in this version. I use database indexes, aggregation pipelines, server-side result controls, document counting, and query-plan inspection as part of the application design. These features improve the usefulness of the class for a larger dataset and show that I can make decisions about how an application should interact with a database rather than treating every query the same way.

The enhancement also gives me stronger evidence for the security outcome. My earlier software-design work improved validation and exception handling, but this milestone focuses more directly on protecting the database boundary. Environment-based credentials reduce the need to place secrets in source code, blocked query operators reduce exposure to unsafe server-side execution, controlled update operators narrow the operations available through the class, and nonempty write filters reduce the risk of accidental mass changes. These controls do not make the application completely secure by themselves, but they demonstrate the security mindset of limiting unnecessary capability and validating data before it reaches a persistent data store.

I also made progress on the outcome involving design and evaluation of computing solutions while considering trade-offs. Indexes can make searches faster, but every index consumes storage and adds work when records are inserted or updated. Server-side aggregation reduces the amount of data transferred to Python, but it places more processing responsibility on the database server. Strict query validation improves safety, but it must be designed carefully so legitimate application queries are not blocked. I do not need to change the outcome-coverage plan I established earlier, but I would now describe the database enhancement as stronger evidence for both the computing-tools outcome and the security outcome than I originally expected.

Reflection on the Enhancement Process

The biggest lesson from this enhancement was that database performance and database security are connected to design decisions made in the application code. In the original version, a successful connection and working CRUD methods were enough to meet the project requirements. While enhancing the class, I had to think about what happens when the collection becomes larger, when a query returns thousands of records, or when an application receives a poorly formed or unsafe filter. That changed my focus from simply making MongoDB respond to making the database interface more predictable and controlled.

Indexing was one of the most useful areas to revisit. It is easy to think that adding more indexes automatically improves a database, but there is a cost to maintaining them. I chose a small set of indexes that match fields already important to the shelter data and added an explain_query() method so index use can be evaluated instead of assumed. The same idea applies to server-side aggregation. My Milestone Three enhancement showed that I understand in-memory algorithms, while this milestone helped me recognize when using MongoDB directly is a better engineering decision because it reduces data transfer and lets the database engine optimize the operation.

The most challenging part was validating MongoDB requests without removing the flexibility that makes MongoDB useful. Queries can contain nested dictionaries, logical operators, arrays, and comparison operators, so a simple check of the top-level keys would not be enough. I used recursive validation to inspect nested query structures and focused on blocking the server-side JavaScript operators that do not belong in this interface. I also kept dependency injections from the earlier enhancement, which allowed the database logic to be tested with a mock MongoDB client. All eleven logic-level unit tests passed during validation without requiring changes to the real AAC collection. Overall, Milestone Four helped me move from basic CRUD programming toward thinking about the database as an engineered part of the application with its own performance, security, and maintainability concerns.
